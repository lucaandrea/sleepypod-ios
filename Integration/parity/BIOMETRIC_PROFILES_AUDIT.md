## Profile and processor portion inspected

Sources: `CalibrationOverview.tsx`, `ProfileRecovery.tsx`, `ProfileLibrary.tsx`, `ProfileComparison.tsx`, `ProfileCandidateEditor.tsx`, `ManualProfileActivation.tsx`, `CalibrationHistory.tsx`; `biometricTuning.ts` routes; `profiles/{contracts,status,history,activation,store}.ts`.

- GET `biometric-tuning/profiles/overview?side`: desired binding (generation, desired/previous UUID, updated milliseconds), desired hash/config/default/warning, runtime health per component, runtime receipts, stage provenance, measured sensor calibration and limitations. Saved intent, processor adoption and present health remain distinct. HRV index is window IBI variability, not clinical RMSSD. Sensor calibration is separate from algorithm personalization.
- GET `biometric-tuning/activation-status?side[&id]`: desired generation, isCurrent, optional event/delivery state, observed state, receipt health and receipts. Polling is read only. An applied past receipt does not establish current health; a selected historical request can be superseded.
- GET `biometric-tuning/activations?side[&beforeGeneration]`: 50-row pages, nextGeneration; action, state, time, reason, requested-by, before/after hashes. Display Pod timezone and reported clock preference.
- GET `biometric-tuning/profiles?side[&beforeCreatedAtMs&beforeId]`: revision pages; cursor fields must be paired. Each revision includes exact manifest/hash/overrides, resolved configuration/hash, dependency hashes, parent, origin/requester, immutable request identity and created time. GET `profiles/{uuid}` reads one revision. Candidate creation never applies it.
- GET `biometric-tuning/manifest`: current manifest/hash and activationAvailable. Numeric editor bounds/defaults/descriptions/units are manifest driven for heart_rate, breathing_rate, hrv_index. Preserve existing stage overrides and reject an incompatible parent/manifest/side. Candidate stage fields are detailed below.
- POST `profiles/resolve` {overrides,baseManifestHash}: resolved configuration/hash, normalized overrides, manifest hash and provenance. Any draft change invalidates review. POST `profiles` sends side, optional parentRevisionId (omit when absent), exact reviewed overrides, baseManifestHash, origin manual, requester and stable idempotency key (max64 overrides). Keep the exact prepared request on uncertain save; do not generate a new key and duplicate a revision.
- POST `profiles/diff` {side,revisionId:null|uuid,againstRevisionId:null|uuid}: before/after hashes, resolved changes and override-intent paths. Bind review to selected side/revision, current generation and before hash. Changing saved generation invalidates review. This is configuration comparison, not agreement validation.
- POST `profiles/{uuid}/validate` with side: schema/engine compatible only, evidence not_checked. Do not label a candidate validated from this response.
- Manual activation routes POST `activate`, `reset`, `rollback`: common side, expectedGeneration, expectedResolvedHash, boundary immediate|next_session, requester, stable idempotencyKey, allowUnvalidated:true. Activate requires exact revisionId UUID; reset omits revisionId; rollback includes UUID or explicit null and must match exact previous binding. User reviews the exact request and unvalidated status. Server handles generation CAS and idempotency. Immediate still means safe processing boundary; next_session waits for known empty-bed boundary.
- Preserve an incompatible pinned revision. Reset recovery can use the overview fallback/default hash with explicit incompatibility warning, because a valid before/after comparison is unavailable. Other activation stays unavailable until a compatible review exists.
- Activation result is a saved event, not processor acknowledgment. Poll its exact ID separately from overview health. Retry only the immutable request/key when delivery is uncertain, respecting server idempotency; changing the request requires a new review.
- Validated activation is separate: GET `validated-activation-review`, POST `activate-validated`, binds exact revision/evaluation/report hash and current generation. Detailed validated-selection/report UI remains to audit with Backtests.

## Native implementation and validation

The Settings route opens a side-scoped Overview with independent profile intent, processor adoption and aged health reports; profile and history pages retain exact pagination. Candidate numeric definitions come from the current manifest, while stage edits reuse the existing rule controls. Saving a candidate does not apply it. A second review binds the action, target, before/after hashes and generation; manual application requires explicit acknowledgement and a processing boundary. Incompatible pinned revisions retain a clearly labelled default-reset path. Schema compatibility is never called agreement validation.

Exact candidate/activation requests are retained before sending, scoped by controller and side, protected on disk and excluded from backup. Unknown results require an explicit retry with the same payload/identity. Another workspace cannot replace an unresolved request or erase a newer one when an old response returns. Stop retrying does not undo a remote change.

The demo stores configuration in memory and reports no processor acknowledgement or validation evidence. Manifest/default fixtures were generated read-only from the Core registry; the overview fixture is synthetic and validated against Core's schema. No physical profile mutations are part of testing.

Full Xcode compilation passes. Seventeen focused checks pass: eight profile/manifest/persistence tests, six lifecycle tests and three literal REST transport tests. Seventeen existing remote-stage regressions also pass: nine model tests and eight rule/parity tests. These cover target-hash activation, generation conflicts, lost replies, stale health, exact retry identity, override intent and competing workspaces.

The candidate → rule edit → resolve → save without applying → comparison → manual application → request → history → recovery flow passes on iPhone dark, iPad light and maximum accessibility text. Final result bundles are `Profiles-final-phone.xcresult` (88.889 seconds), `Profiles-final-ipad.xcresult` (72.041 seconds) and `Profiles-final-accessibility.xcresult`, retained locally under `build/parity-validation/`. Vertical scrolling is expected at maximum text; controls and values wrap within the content width.

Strict SwiftLint, `git diff --check` and the built-product presentation guard pass. The build contains Sleepypod shared components and no retired Free Sleep shell, UI components or asset catalog. Demo tests use synthetic configuration and never claim live processor adoption; no physical Pod profile was changed.
