# Native Autopilot — implementation and evidence

This is one part of the full native parity effort. It does not establish complete web parity or a new TestFlight release.

## Current native behavior

- Sleepypod's gear sheet and All settings open a native Autopilot screen using the existing grouped cards, theme and navigation. Personal comfort remains linked. No retired application shell is included.
- Global switch, rule list, create/edit/duplicate/delete, explicit priority ordering, and Off / Dry run / Active modes. Mode changes use one PATCH for enabled and dryRun. New rules default to dry run; duplicates begin off.
- Native editors preserve Core's complete tagged expression and condition trees: numbers, named signals, aggregates, arithmetic, clamping, All/Any/Not, comparisons, ranges, time windows and days. Trigger intervals, signal changes and times; temperature, power and notification actions; clamp/revert/mode/hold/cooldown fields.
- Validation follows Core's strict union payloads, whole-degree temperature limits, depth and node budgets. Clearing side/cooldown sends explicit null. Existing rules are checked against a fresh server read before editing; the draft survives a conflict and can be explicitly discarded/reloaded.
- Read-only replay of an unsaved draft with side/night choice. Traces keep missing samples as gaps, show replayed setpoints separately from measured values, and distinguish nominal-baseline edge replay from continuous policy replay. Changing a night while replaying cannot display the old response as current or leave Run locked.
- Diagnostics distinguish missing signals, skipped evaluations, dry runs and actual sent commands. A three-hour strip and current-day counts use controller timestamps. Live signal snapshots are explicitly distinct from historical evaluation values.
- Tonight shows the reported owner, manual hold, run-once expiry and last Autopilot temperature command. Times use the Pod's timezone.
- Activity reads up to 30 nights, with outcome filters and manual holds. Boundaries are 6pm in the Pod's timezone, preserving daylight-saving transitions. Recorded spatial pressure zones support side/night selection and frame scrubbing; missing recordings remain explicit.

## Source and transport

Source: Core `src/server/routers/automations.ts`, `src/server/validation-schemas.ts`, `src/automation/types.ts` and `src/automation/backtest.ts`, inspected from owner checkout at `402d827afd85203193af5c3b30787806b469f014` on 2026-10-25.

Typed Core REST paths:

- GET/POST/PATCH/DELETE `automations`
- GET/POST `automations/kill-switch`
- GET `automations/diagnostics`, `automations/tonight`, `automations/nights`
- POST `automations/backtest`, `automations/activity`
- GET `automations/cap-zone-replay`

The Core API currently has no atomic revision precondition for rule writes. The client detects changes visible at its preflight read; it cannot eliminate a server-side race between that read and a write. No actuator requests were sent to a real Pod for these tests.
