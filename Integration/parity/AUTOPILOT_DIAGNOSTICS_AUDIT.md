# Native Autopilot diagnostics and save recovery

This reconciliation keeps Sleepypod's native grouped cards and rule editor. It does not establish a TestFlight release or physical automation qualification.

## Web contract and presentation

Compared `src/components/Autopilot/evaluationStrip.ts` and `StatusPanel.tsx` in Core `7e373fae2b733709453a8f190dc578d30770d2ff` on October 26, 2026. The eight synthetic cases in `Integration/Fixtures/automation-diagnostics-fixtures.json` were generated by the actual web strip, missing-tick and grouping functions. They cover drift grace, periodic gaps, cooldown spans, disabled/nonperiodic rules, outcome precedence, counts, many groups and an empty log. Nested threshold examples retain their signal and aggregation window.

The native diagnostics now include:

- Last evaluation, recorded condition verdict, today's dry runs, fired/clamped evaluations and the separate count actually sent to the bed.
- A three-hour, 180-minute strip with outcome precedence, cooldown bridges and missing periodic evaluations after the first recorded row. An accessible minute stepper complements chart inspection. Missing rows do not prove that the controller was offline.
- Current signal readings and comparison thresholds, explicitly separate from the recorded condition verdict. The complete condition remains visible, including AND/OR/NOT; an individual comparison is not presented as the rule's overall requirement.
- Grouped current-day evaluation history with All/Would/Fired/Skipped/Missing filters and ten more groups per expansion. Counts represent evaluations, not groups. Unreadable timestamps/outcomes and future rows are excluded explicitly.
- Editing and atomic mode changes from each rule's diagnostic card. Active mode retains its existing confirmation. Global halt uses the existing kill-switch contract; no additional recovery endpoint is invented.

The native night-planning, multi-night replay, activity and pressure playback work is documented in `AUTOPILOT_PLANNING_VALIDATION.md`. Personal comfort's capability and qualification boundaries are documented separately in `PERSONAL_COMFORT_AUDIT.md`.

## Save and lifecycle behavior

Writes are scoped to the connection that opened the workspace. An owner change or invalidated preflight cannot send a rule mutation. An unconfirmed sent mutation requires an explicit fresh read; background refresh cannot silently unlock retry.

A lost create response retains the draft and blocks new creation. A fresh rules read may identify one new rule with the exact submitted definition; the editor then adopts that saved rule for review without creating it again. No match or multiple matches leave the result uncertain. The editor places its recovery message first and dismisses the name keyboard when saving.

Core still has no atomic rule revision precondition or create idempotency token. Existing-rule preflight detects changes visible before dispatch but cannot close the server-side race. Recovery is scoped to this open workspace; it is not a durable hardware-command receipt. No real Pod mutations were used for validation.
