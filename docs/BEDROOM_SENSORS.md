# Bedroom sensor context

The native app consumes the authenticated `GET /api/v1/home/bedroom` contract from our Core fork. Open **Settings → Room sensors → Bedroom devices**. Once sources are mapped, their summary also appears in Temperature and Schedule.

Each physical device retains its name, location, provider, measurement units and reporting clock. Cached, expired, unavailable and disabled readings display a dash; they cannot become live simply because a controller request succeeds. Device power, fan speed, air-quality categories and particle concentration remain distinct. Temperatures are canonical Fahrenheit on the wire and follow the app's display-unit preference.

The app checks source identity, timestamps, lease duration and configuration consistency. A receipt expires after 15 seconds, values expire at their source deadline, and leaving the foreground or switching controllers withdraws live values. Receipt age uses elapsed local time against the controller clock, so a phone clock offset cannot extend a reading.

**Choose room inputs** edits the saved configuration using its expected revision. Concurrent edits are rejected; an unknown save outcome leads to a read, not an automatic write retry. Every configuration change requires publishers to use the new revision.

Personal Comfort offers **Include bedroom climate** when the controller supports it. It preserves the option when editing other settings and includes the bedroom configuration in owner qualification identity. The controller remains the sole temperature authority; source selection alone does not activate Autopilot or change wake alarms.

## Verification

- `Integration/Fixtures/bedroom-context-core.json` was generated by Core's migrated SQLite store and validated against its output schema. All devices and values in this file are synthetic.
- Contract tests cover five-device decoding, cached readings, source/receipt expiry, background withdrawal, malformed clocks, concurrent edits, lost save replies, transport paths and room-aware qualification identity.
- The iPhone and iPad UI test navigates to all five fixture devices and checks the cached-reading state. The fixture is available only in Debug and only when Demo plus `uiBedroomFixture` is explicitly selected.
- The full native unit/transport run passed 959 tests with 8 existing skips before the final owner-identity and transport additions; the subsequent iPad-focused run passed all 21 tests, including those additions and the UI test.
- The final reporting-clock and lease validation changes passed all 11 bedroom contract/transport tests. SwiftLint reports no violations.

This change does not install sensor publishers or claim real HomePod availability through Apple's public API. Persistent home-server publishing, source qualification, physical-device release and overnight Preview observations are separate deployment gates. Existing HomeKit/Homebridge pairings remain in place.
